# PROSPER Well Agent — демонстрационная версия

## Что изменено

Проект теперь демонстрирует полный агентный контур, требуемый НИР-4:

**инженерный запрос → LLM → типизированная задача → валидация → MCP → результат → журнал.**

Реальный PROSPER/OpenServer пока не подключён: вместо него используется прозрачный `MOCK_PROSPER`-адаптер. В ответах явно указано `integration_status=NOT_CHECKED`. Это не является доказательством интеграции с реальным PROSPER.

Архитектура подготовлена так, чтобы позднее заменить только MCP-адаптер на вызовы установленного PROSPER/OpenServer.

## Быстрый запуск

Python 3.11+ рекомендуется.

```bash
python -m venv .venv
# Windows PowerShell
.venv\Scripts\Activate.ps1
# Windows cmd
# .venv\Scripts\activate.bat

pip install -r requirements.txt
```

Для живой LLM:

```bash
copy .env.example .env
# задайте OPENAI_API_KEY в .env или переменной окружения
python main.py "Проверь НКТ скважины W-31: наружный диаметр 73 мм, стенка 5,5 мм, внутренний диаметр 62 мм"
```

Для проверки без API-ключа:

```bash
python main.py --offline "Проверь НКТ скважины W-31: OD 73 мм, стенка 5,5 мм, ID 62 мм"
```

## Что показать преподавателю

### 1. Успешный сценарий

```text
python main.py "Проверь НКТ скважины W-31: наружный диаметр 73 мм, стенка 5,5 мм, внутренний диаметр 62 мм"
```

Ожидается `PRECHECK_OK`.

### 2. Ошибка входных данных

```text
python main.py "Проверь НКТ скважины W-31: OD 73 мм, стенка 5,5 мм, ID 80 мм"
```

Ожидается `INVALID_INPUT`.

### 3. Запрос вне области агента

```text
python main.py "Рассчитай стоимость бурения скважины"
```

Ожидается `OUT_OF_SCOPE`.

### 4. Создание новой модели

```text
python main.py "Подготовь создание новой модели скважины W-31 по комплекту New"
```

Ожидается `PLAN_READY`. Записи в реальный PROSPER нет.

### 5. Обновление модели

```text
python main.py "Подготовь обновление модели скважины W-31 после ремонта Rep"
```

Ожидается `PLAN_READY` с `confirmation_required=true`.

## Где видно работу LLM

`logs/llm_calls.jsonl` содержит:

- исходный инженерный запрос;
- `trace_id`;
- типизированную задачу, которую получила система после разбора;
- модель;
- режим `openai_responses` или `offline_fallback`.

`logs/agent_runs.jsonl` связывает разбор LLM с итоговым `AgentResult`.

`logs/mcp_calls.jsonl` содержит фактические аргументы и ответы MCP-инструментов.

## Почему PROSPER пока MOCK

В задании требуется реальный расчётный сценарий в установленном ПО; заглушка сама по себе интеграцию не подтверждает. Поэтому проект намеренно не называет mock-запуск расчётом PROSPER. До получения ПО этап интеграции имеет статус `NOT_CHECKED`.

После получения доступа к PROSPER/OpenServer нужно заменить реализации:

- `check_tubing` — при необходимости оставить как preflight-проверку;
- `prepare_new_model_plan` → реальный MCP-инструмент создания/заполнения модели;
- `prepare_update_model_plan` → реальный MCP-инструмент работы с копией модели и diff.

Оркестратор агента (`agent.py`, `loop.py`, схемы и журнал) при этом сохраняется.

## Безопасность записи

Текущие mock-инструменты ничего не записывают в PROSPER. Для будущей интеграции оставлен отдельный шаг подтверждения: план изменений должен быть показан инженеру до операции записи.

## Ограничения текущей демонстрации

- PROSPER/OpenServer физически не запускается;
- точность инженерной модели PROSPER не оценивается;
- данные синтетические;
- реальные поля OpenServer должны быть сверены с документацией и установленной версией ПО после получения доступа.
