
# PROSPER AI Agent
### Интеллектуальный агент для создания и обновления моделей нефтяных скважин

## 1. Описание проекта

**PROSPER AI Agent** — система автоматизации инженерных операций в программном комплексе PROSPER (Petroleum Experts) с использованием большой языковой модели (LLM) и протокола Model Context Protocol (MCP).

Проект разрабатывается в рамках научно-исследовательской работы (НИР № 4).

Основная цель — разработать AI-агента, который обрабатывает инженерные запросы на естественном языке, извлекает данные из технической документации, проверяет их корректность и взаимодействует с PROSPER через MCP-инструменты.

Система предусматривает два сценария:

- **New** — создание модели новой скважины на основании комплекта исходных документов.
- **Rep** — обновление существующей модели после ремонта скважины.

Оба сценария используют общие компоненты обработки документов, проверки данных, взаимодействия с программным обеспечением и журналирования операций.

## 2. Постановка задачи

Необходимо разработать AI-агента для автоматизированного создания и обновления моделей скважин в PROSPER.

Агент должен:

1. Принимать инженерный запрос на естественном языке.
2. Преобразовывать запрос с помощью LLM в структурированную типизированную задачу.
3. Определять необходимые исходные документы.
4. Извлекать инженерные параметры из документов.
5. Проверять полноту, единицы измерения и физическую корректность данных.
6. Формировать манифест исходных данных с указанием источников значений.
7. Подготавливать операции создания или изменения модели.
8. Запрашивать подтверждение инженера перед записью.
9. Вызывать инструменты PROSPER через MCP-сервер и OpenServer.
10. Сохранять модель и считывать параметры обратно.
11. Выполнять контрольный расчёт.
12. Формировать отчёт и журнал операций.

Числовые расчёты выполняются специализированным ПО или проверяемым расчётным кодом. LLM отвечает за интерпретацию запросов и организацию последовательности действий, но не подменяет инженерные вычисления.

## 3. Сценарии использования

### 3.1. New — создание новой модели

**Входные данные:**

- инклинометрия скважины;
- характеристики насосно-компрессорных труб (НКТ);
- паспорт электроцентробежного насоса;
- паспорт погружного электродвигателя;
- протоколы испытаний оборудования;
- дополнительные технические акты;
- подтверждённая PVT-модель соответствующего пласта.

**Последовательность выполнения:**

1. Загрузка комплекта документов New_*.
2. Инвентаризация файлов и проверка полноты.
3. Извлечение параметров скважины и оборудования.
4. Приведение данных к согласованным единицам.
5. Проверка траектории, компоновки и характеристик оборудования.
6. Формирование манифеста данных.
7. Подготовка модели PROSPER.
8. Подтверждение операции инженером.
9. Создание и сохранение модели.
10. Повторное чтение параметров.
11. Контрольный расчёт и сравнение с ручным запуском.

**Ключевые проверки:**

- NEW-01 — корректность траектории;
- NEW-02 — согласованность TVD и системы отсчёта;
- NEW-03 — корректность НКТ;
- NEW-04 — соответствие паспортам;
- NEW-05 — характеристики оборудования;
- NEW-06 — PVT и характеристики ПЭД;
- NEW-07 — сохранение и обратное чтение модели;
- NEW-08 — воспроизведение расчёта;
- NEW-09 — переносимость между комплектами.

По заданию необходимо выполнить инвентаризацию 14 комплектов и продемонстрировать расчётный сценарий минимум на трёх согласованных скважинах.

### 3.2. Rep — обновление модели после ремонта

**Входные данные:**

- комплект документов Rep_*;
- базовая модель PROSPER;
- сведения о предыдущей компоновке;
- документы о ремонте;
- подтверждённые изменения оборудования.

**Последовательность выполнения:**

1. Загрузка базовой модели.
2. Проверка идентификатора скважины и версии.
3. Анализ ремонтной документации.
4. Определение изменённых параметров.
5. Формирование diff между исходной и новой моделью.
6. Отображение изменений инженеру.
7. Получение подтверждения.
8. Создание копии базовой модели.
9. Применение изменений к копии.
10. Сохранение и обратное чтение.
11. Контрольный расчёт до и после ремонта.
12. Проверка повторного выполнения запроса.

**Ключевые проверки:**

- REP-01 — соответствие базовой модели;
- REP-02 — подтверждённость изменений;
- REP-03 — сохранение неизменяемых параметров;
- REP-04 — подтверждение записи;
- REP-05 — разрешение конфликтов;
- REP-06 — проверка сохранённой модели;
- REP-07 — обработка ошибки записи;
- REP-08 — расчёт до и после ремонта.

По заданию необходимо провести инвентаризацию 7 ремонтных комплектов и продемонстрировать обновление трёх согласованных моделей.

## 4. Архитектура AI-агента

```text
              Запрос пользователя
                       |
                       v
                LLM / AI Agent
                       |
                       v
            Типизированная задача
                       |
                       v
               Validation Layer
                       |
                       v
             Document Processing
                       |
                       v
               Source Manifest
                       |
                       v
                 MCP Client
                       |
                       v
                  MCP Server
                       |
                       v
               PROSPER Adapter
                       |
                       v
               OpenServer API
                       |
                       v
                    PROSPER
                       |
                       v
            Результат / Diff модели
                       |
                       v
          Подтверждение инженера
              (перед записью)
                       |
                       v
          Сохранение / Обратное чтение
                       |
                       v
           Контрольный расчёт / Отчёт
```

Схема отражает логические компоненты системы. Перед выполнением изменяющей операции агент обязан получить подтверждение инженера.

### Основные компоненты

| Компонент | Назначение |
|---|---|
| LLM Agent | Интерпретация инженерного запроса |
| Task Schema | Типизированное представление задачи |
| Document Parser | Извлечение данных из документов |
| Validation Layer | Проверка данных и единиц измерения |
| Source Manifest | Прослеживаемость исходных значений |
| MCP Client | Вызов доступных MCP-инструментов |
| MCP Server | Интерфейс инженерных операций |
| PROSPER Adapter | Взаимодействие с OpenServer |
| Confirmation Layer | Подтверждение изменяющих операций |
| Logger | Регистрация действий и ошибок |
| Report Generator | Формирование инженерного отчёта |

## 5. MCP и интеграция с PROSPER

Для интеграции используется интерфейс OpenServer установленной версии Petroleum Experts IPM.

Документация OpenServer различает следующие операции:

- `DoSet` — установка параметров;
- `DoCmd` — выполнение команд;
- `DoGet` — чтение параметров и результатов.

Для PROSPER предусмотрены операции создания, открытия и сохранения модели, включая:

- `PROSPER.NEWFILE`
- `PROSPER.OPENFILE`
- `PROSPER.SAVEFILE`

Точные адреса параметров и расчётные команды должны быть подтверждены по документации установленной версии и проверены на реальной модели.

Запись в глобальную базу оборудования не входит в базовый объём проекта без подтверждения соответствующего API.

## 6. Формат входных данных

Пример инженерного запроса:

> Создай модель новой скважины по комплекту New_1042. Проверь траекторию, НКТ, насос, ПЭД и подготовь модель к сохранению.

Пример структурированной задачи:

```json
{
  "case_id": "NEW-1042-DEMO",
  "scenario": "NEW",
  "well_id": "1042",
  "source_folder": "New_1042",
  "operation": "prepare_model",
  "requires_confirmation": true,
  "confirmed": false
}
```

Это иллюстративный пример контракта агента, а не подтверждённый результат обработки реальных документов.

## 7. Формат результата

Пример ответа после подготовки операции:

```json
{
  "case_id": "NEW-1042-DEMO",
  "execution_status": "SUCCESS",
  "validation_status": "NOT_ASSESSED",
  "model_saved": false,
  "requires_confirmation": true,
  "message": "Подготовка операции завершена. Ожидается подтверждение инженера.",
  "trace_id": "demo-trace-001"
}
```

Здесь `SUCCESS` означает только успешное выполнение этапа подготовки. Он не подтверждает точность инженерной модели.

## 8. Пример обработки ошибки

Если обязательное поле отсутствует, агент не должен подставлять произвольное значение.

Пример:

```json
{
  "case_id": "NEW-1042-DEMO",
  "execution_status": "ERROR",
  "error": {
    "code": "MISSING_REQUIRED_FIELD",
    "field": "pump_model",
    "message": "Не подтверждена модель насоса",
    "action": "Запросить паспорт или подтверждение инженера"
  },
  "model_saved": false,
  "trace_id": "demo-trace-002"
}
```

При такой ошибке зависимая операция записи блокируется.

### Обязательные проверки устойчивости

Система должна обрабатывать:

- отсутствие обязательного значения;
- неизвестные или неверные единицы;
- выход параметра за допустимый диапазон;
- неразобранный документ;
- недоступность инженерного ПО;
- занятую лицензию (`LICENSE_BUSY`);
- превышение времени выполнения (`TIMEOUT`);
- отсутствие численного решения (`NO_SOLUTION`);
- отказ инженера от записи;
- повторное выполнение запроса;
- попытку внедрения инструкций через документ.

Для тестирования ошибок лицензии и таймаута допускается тестовый адаптер. Такие сценарии должны быть явно помечены как имитационные.

## 9. Проверка результатов

Предусмотрены четыре уровня проверки:

| Уровень | Метод |
|---|---|
| Перенос данных | Сравнение с подтверждённым манифестом |
| MCP-интерфейс | Проверка схем и статусов инструментов |
| Расчётный адаптер | Сравнение с ручным запуском PROSPER |
| Инженерная модель | Сравнение с независимыми промысловыми измерениями |

**Важно:** успешный вызов MCP не доказывает физическую точность модели. Совпадение автоматического и ручного расчётов подтверждает воспроизводимость автоматизации.

Допуски сравнения должны быть утверждены до выполнения расчётов. Без установленного допуска результат получает статус `NOT_ASSESSED`.

## 11. Подготовка окружения

Планируемое окружение:

- Python 3.10+
- установленный PROSPER и OpenServer для интеграционных испытаний;
- доступ к согласованной модели скважины;
- Python-библиотеки, необходимые для конкретной реализации MCP и парсинга.

Создание виртуального окружения:



```bash
pip install -r requirements.txt
```


## 12. Ограничения

- Исходные документы могут содержать неоднозначные поля и единицы.
- Критичные распознанные значения требуют подтверждения.
- Исходные инженерные файлы открываются только для чтения.
- Изменение модели выполняется исключительно на копии.
- Запись разрешается после подтверждения инженером.
- Доступность API зависит от установленной версии OpenServer.
- Полноценная интеграция требует лицензии и доступа к PROSPER.
- При отсутствии промысловых замеров нельзя заявлять о точности модели относительно реальной скважины.
- Секреты, производственные модели, архивы и сканы не публикуются в открытом репозитории.
